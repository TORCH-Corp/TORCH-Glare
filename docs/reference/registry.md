# Registry Format

`torch-glare` installs components over HTTP from the `registry/` directory on the Glare
repository, served by raw.githubusercontent.com:

```
https://raw.githubusercontent.com/TORCH-Corp/TORCH-Glare/main/registry
```

The directory is generated by `pnpm run registry` and committed, so what is served is exactly what
the generator emitted. This page describes that format; a machine-readable JSON Schema is published
alongside it at [`schema.json`](https://raw.githubusercontent.com/TORCH-Corp/TORCH-Glare/main/registry/schema.json), and the test suite validates every emitted item
against it.

## URLs

```
GET <registry>/index.json           every item, its dependencies and its file list
GET <registry>/schema.json          this format, as JSON Schema
GET <registry>/<type>/<Name>.json   one item, with its source inlined
```

Any git ref works in place of `main`, so a tag serves that release's registry unchanged.

`<type>` is one of `components`, `hooks`, `utils`, `layouts`, `providers`. It is both the item's
kind and the sub-folder it installs into.

**A dependency reference is a URL path.** `registryDependencies` entries look like
`components/Button`, so a consumer resolves one by concatenation — `<registry>/components/Button.json`
— with no lookup table and no mapping rules.

## The index

Fetched once per install. The CLI resolves the whole dependency closure from it locally rather than
walking the network item by item.

```jsonc
{
  "version": "2.5.6",
  "generatedBy": "scripts/bin/generateRegistry",
  "npmVersions": {                    // package -> range, shared by every item
    "@tanstack/react-table": "^8.21.3"
  },
  "items": [
    {
      "name": "Table",
      "type": "components",
      "path": "components/Table.tsx",           // file or directory, relative to the library root
      "files": ["components/Table.tsx"],        // the expansion of `path` when it is a directory
      "npmDependencies": ["class-variance-authority"],
      "registryDependencies": ["components/Button", "utils/cn"]
    }
  ]
}
```

## An item

Self-contained: everything needed to install it, without the index.

```jsonc
{
  "version": "2.5.6",
  "name": "Table",
  "type": "components",
  "dependencies": ["class-variance-authority@^0.7.1"],   // ranges inlined
  "registryDependencies": ["components/Button", "utils/cn"],
  "files": [
    {
      "path": "components/Table.tsx",     // where it lives in the library
      "target": "components/Table.tsx",   // where it installs, relative to the configured `path`
      "content": "import React from \"react\";\n…"
    }
  ]
}
```

### Why the two shapes name dependencies differently

The index says `npmDependencies` with bare package names and hoists the ranges into one
`npmVersions` map. An item says `dependencies` with the range inlined. That is deliberate, not an
oversight:

- The index is fetched **whole, on every install**, so it stays small — one shared map instead of
  the same range repeated across 92 items.
- An item has to **stand alone**. Fetched on its own it has no `npmVersions` to consult, so the
  range travels with it — and the CLI prefers it for exactly that reason. `dependencies` is also
  the key shadcn registries use, which makes the payload familiar.

## Rules a registry must honour

- **`target` must stay inside the install directory.** The CLI rejects any item whose `target`
  escapes it. Paths come off the network; they are not trusted.
- **`files` must be non-empty**, and every `content` a string. An item that lists no files installs
  nothing, which is worse than failing.
- **Every `registryDependencies` ref must resolve** at `<base>/<ref>.json`. The CLI errors rather
  than installing a partial closure.
